# 首轮时序检查修复（2026-10-23）

本轮修复离线测试夹具和断言。App 仍为 Build 75；所有生产源码保持上一轮最终版本，长任务默认开启、无限制总步数、历史压缩、原始目标与子任务保留、暂停/继续、停止及异常保护不变。

## 查明的测试缺陷

首轮完整检查与双平台编译同时运行时，旧断言报：

```text
Each frame wait sends at most one short wake pair: unchanged
```

旧断言检查整个任务累计移动数是否在 `3...4`，而一次单步任务包含初始取屏与模型返回后验证两次独立等待。初始来源确认早到时可以零唤醒，合法任务总数可以为 2，甚至两次等待都已收到确认时为 0；累计总数不能代表每次等待是否超出一对。旧故障注入同样依赖累计移动数，初始取屏零唤醒时会把后续校验错认成初始阶段，漏掉换源/换像素/停止/静默故障。

另一个缺陷是旧离线来源只在移动回调更新一次确认时间，随后不再提供 complete/idle 回调。若回调后消费延迟超过 1.5 秒，确认真实过期，生产引擎会在 6 秒期限安全失败。旧测试仍将这种状态报成笼统的次数断言错误。对照实验还证明，校验阶段超时可能得到累计 4 次移动，旧次数断言反而通过。

首轮旧日志没有保存实际移动数、capture span、phase 或 error，无法确定那一次进入了上述哪条分支。受控实验复现的是可验证的失败机制，不能据此宣称当时一定发生了 CPU 调度超时。原始失败日志和全部对照实验保留在本轮输出中。

## 修复

- 根据真实生产 `.capture` span UUID 归属每一次实际移动，按每次等待验证至多两次、顺序 `+3/-3`、零按键。
- 按模型阶段和当前 span 注入故障；初始取屏无唤醒时仍实际验证换源、换像素、停止与静默保护。
- 离线来源通过显式回调更新确认时间，保留原像素采集时间和对象，复用生产 `FrameReadinessGate`。读取 frame 不制造新证据。
- 慢模型使用 continuation 门控，取消后交付旧回复仍不能产生动作；不再用固定 2 秒模型睡眠区分阶段。
- 1.7 秒受控消费延迟同时保留两个对照：没有后续回调则旧证据过期、零点击；有独立 idle 回调则恢复。无来源和静默来源仍真实等待生产 6 秒超时。
- 每个场景在断言抛错之前保存完整 JSON，包含移动、阶段、回调/像素/确认时间、模型次数、phase/error 和逐项断言。

生产 1.5 秒新鲜度、6 秒等待、每次等待单次唤醒尝试与停止保护没有修改。测试中的一次或两次轻移都是离线执行器记录，不是真实手机操作。

## 完整回归暴露的相同时钟 tick 问题

本轮完整回归的最后一个流程集成夹具曾报 `capture replay exhausted`。只在耗尽时输出的低扰动回放在第 4 次复现：`visualTape` 点击后手工交付的新帧，其像素时间、确认时间和生产驱动要求的边界完全相同（浮点 bitPattern 也相同）。生产严格 `>` 检查正确拒绝该帧，夹具却假设连续调用 `Date()` 必定得到更晚时间，进入了空队列。这与新取屏 helper 的 opt-in hooks 无关；该集成测试是独立进程，hooks 均为 nil。

修复仅限 `Tests/WorkflowIntegration/main.swift` 的合成来源：默认交付时间须等真实时钟跨过调用入口和上一帧，`next(after)` 须先跨过实际边界再消费队列；显式旧时间仍用于过期反例。等待按单调时钟限时，不加未来 epsilon，不放宽生产 `>`。失败日志、时间与堆栈、原失败源码包及修复后重复回放结果均保留在本轮输出。
