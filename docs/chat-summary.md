# WP7 聊天读取与证据总结

这条生产链路把聊天读取、证据保存和模型总结分开。**当前 App 的 OCR 不能证明会话最新端，也不能取得真实消息 ID。可用的条数范围是用户明确选择的“当前可见页”：仅核号进入后的首个可见页面，固定选中已识别样本，不称为最近 N 条；多页/续读关联仍不猜测同文重叠。**模型仅在已接受证据保存后生成总结。本轮验收全部使用离线 fixture，没有打开、读取或上传用户的真实私聊，也没有调用真实模型接口。

## 入口与边界

- 用户必须指定稳定会话标识、当前设备，以及当前可见页最多多少条（1…200）或绝对起止时间。`scopeID` 绑定整份请求；恢复时不能沿用同一标识偷偷改会话、设备或扩大范围。
- 旧 `.latest(count:)` 编码保留供历史档读取；当前没有独立最新端能力，因此严格最近 N 请求返回 `latestEndUnknown`，不读取资料/消息、不导航、不滚动、没有可上传的 selectedMessages。新空范围保存 partial，已有旧 complete/帧/v2报告不因被拒绝的重试而回写。旧报告可查看、原始 JSON 可原样导出；只读 Markdown 会明确最新端未验证，不能据它再次上传模型。v2 段复用也在调用前受同一限制。
- 新 `.currentPage(limit:)` 只接受首个独立核验的聊天页：按可见顺序取末尾最多 limit 条并按原序输出；绑定 scope、请求目标、frameID、原始像素时间、limit 和精确本地消息 ID 集合。观察数、选中数和未识别媒介分别说明；完成仅指该页样本。绑定后相同 scope 不允许再次读取、向前/新增、换页或扩大条数，生产入口和 Store 同时拒绝，不能只靠 UI 禁用。要读新页必须显式新建范围。
- `ChatEvidenceReader.read(request:direction:nextFrame:scroll:)` 接受真实截图/OCR驱动闭包。`nextFrame` 返回 `ChatEvidenceFrame`，`scroll` 执行一次当前会话的有界滚动。Reader 不自行打开联系人，不接受模型提供的坐标。
- `ChatEvidenceFrame.from(snapshot:)` 是现有 `PhonePageAdapters` 的保守适配器。当前 OCR 必须同时看到微信会话结构、精确标题和独立“手机/电脑互传文件”系统说明，才能证明内置文件传输助手。只看到联系人显示名不会开始读取。
- 已有历史的内置助手也可由用户先打开个人资料页，再经 `WeChatConversationDriver` 核对准确名称、唯一保留账号 `Weixin ID: filehelper`、完整专属设备/电脑互传说明、独立 Messages 按钮及实际返回/更多图形，只点一次当前 Messages，沿既有资料到聊天的真实时序建立 `contactProfileNavigation`。通用 Details、同名联系人或聊天正文复制说明都不构成身份；账号 OCR 有误即停止，不做纠错。保存的资料证据不能恢复 live 权限。英文优先全屏 OCR 漏中文名时，仅 `workflowSnapshot` 在完整原始资料候选内对同一帧标题区域补做真实中文 OCR；无预设名称或账号替换，通用读屏缓存和长任务路径不变。两张真实资料截图的静态本地回放通过，不代表已通过手机导航或聊天读取。
- 经资料独立核号进入内置助手时，若当前聊天页有唯一一条按既有精确文字、OCR 来源和居中几何识别的互传系统说明，仅从新消息 rows 排除该元素 ID；原聊天 snapshot、资料证明和导航时序完整保存。没有此说明时照常读取实际消息；有两条或更多合格说明候选则返回 `ambiguousContinuity` 并停止，不猜选一个，也不把它们当消息事实。普通联系人即使同名、正文和几何相同也不受过滤；助手中相同文字位于系统说明几何之外的消息仍保留。直接内置助手工厂保持原有唯一说明核验规则。
- 真实读取每次创建新的 `ChatEvidenceCaptureAdapter`。首帧仍必须取得独立身份证据。一次 `adapter.scroll(_:perform:)` 只允许一次后续观察；后续 OCR 没有独立消息发生位置证据时，返回 typed `unmerged`，立即撤销临时权限。相同 capture、设备、标题和结构以及局部唯一的同文序列，也不能证明是同一批消息。
- 普通刷新、导航、共享重启、设备/标题变化或滚动失败均撤销临时绑定。每次恢复或新 `readChat` 必须重新证明身份；磁盘证据及未合并批次不能恢复 live 权限。旧 `controlledScroll` 仅保留历史验证/读取兼容，新 live adapter 不再生成此种证明。
- 普通联系人通过 `WeChatConversationDriver` 从用户已打开的真实个人资料页进入：授权稳定 ID 为 `wechat.account:<屏幕精确微信号>`，同时核对资料姓名、微信号、朋友圈、“发消息”和“音视频通话”等专属结构。只点一次当前可见“发消息”，再以同 capture/设备的真实会话结构建立 `contactProfileNavigation` 证明；原资料 OCR、来源控件和点击时间均归档。不会搜索同名联系人，也不会伪造 `platform_identity` 元素。
- 已验证资料导航后的空输入框可能没有 OCR 占位文字。此时仅在既有账号证明下接受本地实际像素检测的返回、更多和添加三图形，加上唯一准确标题；`source` 必须为 `local_visual`，三图形位置和尺寸均受限。模型或 OCR 中写着“视觉:添加”等字符串不能冒充像素检测。全局 `PhonePageAdapters` 不因此放宽为昵称即可识别账号。
- 平台若确实提供稳定身份，仍可走 `verifiedPlatformID`，但必须是真实 `platform_identity` 来源；普通联系人生产驱动不会创建此种伪元素。上述两种独立证明均缺失时立即停止。
- `reachedBoundary` 只允许由驱动在观察到明确历史边界后设置；无新增画面本身不能证明完整覆盖。

## 消息与连续性

每条消息保留原文、发言人（未知为 `nil`）、发送时间及原始时间标签、来源画面、元素标识、归一化位置、画面采集时间，以及未读取的语音/图片/视频/附件。采集时间不代替发送时间。只有显式包含年份的绝对日期和已知设备时区才解析为发送时间；“昨天 10:00”等标签保留但不推算日期。指定时间范围排除绝对时间未知的消息，并在报告中说明范围缺口。

时间范围的新合并必须由独立真实平台消息 ID 及一致字段逐条证明重叠；App 目前的 OCR 工厂不提供此能力；真实消息 ID 本身也不证明消息位于会话最新端。离线测试的 synthetic platform IDs 只测试可信边界协议，不能称为真机 OCR 能力。仅有 GUI/OCR 时，即使至少两条序列在两帧各自唯一，也可能是历史中不同的两次同文发送，必须暂停。单帧每条实际观察仍有独立 `m-…` 本地引用编号，不能冒充微信消息 ID。

未验证的第二页保存在同一 `PhoneAgent/chat-evidence.json` 会话内的可选 `unmergedBatches`。其中只有原始 snapshot/rows、请求 scope/目标 tag、方向、固定未验证原因和来源前帧，无会话证明。它不进入 `frames/messages`、消息计数、selectedMessages、引用、总结或 bootstrap。Reader 原子保存后置 `ambiguous`，不再滚动；合并失败的临时 anchors 不得污染已接受消息。文件权限为 `0600`，`frames + unmergedBatches` 合计最多300，整份文件最多40MB，坏来源/几何/时间/跨数组ID冲突拒绝，写入失败不推进内存。

旧档没有 `unmergedBatches` 时仍原样读取、保存和导出，不自动迁移、不删原始消息、帧或报告。旧 `controlledScroll` 以及无ID的跨帧 anchors 只是旧连续性规则的保留记录；旧 `complete` 或 v2 总结段不能证明重新核验了发生位置。时间范围的新总结会明确警告此限制，未合并数据绝不自动提升为已读消息。旧 latest 无最新端证明则直接禁止新总结；原报告和字段仍保留。

指定绝对时间范围需要有序证据覆盖两侧：older 先见严格晚于 end 的起始侧，再见严格早于 start 的终止侧；newer 反向。同一独立页面已覆盖严格两侧也可以完成。起点在范围内、错误侧、只有单侧历史边界、未知时间或已知时间顺序冲突都保持 partial；原顺序和原时间不排序修补。当前未复核旧运行的两侧权威，不能从旧完成状态继承覆盖。最后一个获准页面保存后立即停，不为已耗尽的分页或原始证据预算再发滚动。

## 总结、引用与导出

`ChatEvidenceSummarizer(model:)` 注入应用已配置的文本模型闭包；沿用已有模型/隐私检查和凭据，不创建 Key。每批最多 30 条、完整 prompt 最多 14000 字符；超过上限继续分批，原文不截断。模型只接收所选消息。currentPage 只取已固定 ID 集合，不能把同页其余观察、raw 或后续页发给模型；legacy latest 在模型调用和已存 v2 复用之前即拒绝。分段摘要逐批保存；第二批失败后恢复不会再次提交已经保存的第一批。

时间范围的增量总结把新增消息标为 `newMessageIDs`，复用已完成的分段摘要，并带最多 10 条已存原消息作为更正/冲突上下文；每个新结论必须至少引用一条新增消息。更早且未携带的跨段语义关系不自动判定，报告保留全部已存条目及消息顺序。

当前分段和报告使用可选 `validationVersion: 2` 与 `cs-v2-` / `cr-v2-` UUID 标记配对；未知版本、保留新版标记却删除版本、或版本2配旧标记均拒绝。它是格式一致性规则，不是密码学防篡改。没有此字段的既有 v1 存档仍按原有来源校验读取，完整原消息、旧 segment 和旧报告不重写；旧版报告明确标记验证限制，更正项中最后引文不支持的活动负责人/期限不展示，原始 JSON 字段及前后引文仍保留。加载、预览和导出不会自动请求模型。

旧 segment 不作为新版验证结果复用。用户显式点总结时，会重新处理当前选中的原消息范围一次，生成严格的 v2 分段与报告，同时保留旧历史；这次格式升级不能宣称仅处理新增消息。之后未变化的 v2 分段恢复增量复用。

严格 JSON 输出包含关键事实、明确决定、明确待办、模型推断、冲突和更正。每条结论必须引用实际存在的消息和连续逐字摘录；负责人、期限需逐字出现在摘录中，相对期限保持原词。冲突/更正至少引用两条且按原顺序排列；推断不能携带负责人/期限冒充承诺。程序拒绝不存在的引用、改写的引文、倒序冲突、未处理媒介的内容结论和额外 JSON 字段。

v2 更正项的非空负责人/期限必须由最后一条按序引文逐字支持；不能从被更正的旧引文取出旧字段作为更正后的活动值。最后引文没有重述的字段须留 `null`，不推定保持不变；不合规则的模型字段会使该批拒绝。结论按完整 tuple（类别、总结文字、有序消息ID和逐字引文、负责人、期限）稳定去重；相同文字出现在不同消息 ID 时继续保留。去重前仍限制模型输出 500k 字节、原 claims 最多200项，不能用大量重复绕过预算。验证保证来源与这些结构规则，不自动证明任意自然语言概括或承诺分类的语义正确。

引用及摘录校验不能自动证明模型概括在语义上完全忠实；报告保留来源供复核。无文字气泡和未被 OCR 识别的媒介覆盖范围仍未知，不能据此声称读取了所有附件内容。未读范围、未知时间/发言人、未处理媒介、实际条数和部分完成状态均在报告内标记。

`ChatSummaryReport.markdown()` 生成可读报告；报告、分段摘要及完整会话均为 `Codable`，应用可以通过 `JSONEncoder` 导出包含所有来源锚点的 JSON。证据层不会自动发送报告或读取其他会话。联系人资料导航产生的 bootstrap 临时许可只在进程内保存并单次消费，不写入 JSON；即使完整资料证明被存档，也不能据它恢复新运行的读取权限。

### 由构造保证原始证据不变的追加事务

总结器使用 `ChatEvidenceStore.appendSummary(_:sessionID:expectedSelectedMessageIDs:updatedAt:)` 和 `appendReport` 保存产物。两者是同步、受限的 typed append：从 Store 当前私有且已完整验证的 Document 取得目标会话，只追加摘要或报告并更新 `updatedAt`，返回最新会话。调用者不能传入整份原始 Session、修改闭包或跳过校验的授权；模型等待期间已经保存的其他摘要、报告和范围继续保留。事务逐项比较选中消息 ID 的原有顺序；这个前置条件不等于对任意消息内容的字节一致性检查，也不提供新的读取或上传范围。

只有这个私有构造路径可复用原始值已通过的三段验证：已接受帧、未合并原始批次、消息与来源锚点关联。`init` 与通用 `save(_:)` 对外部数据仍完整执行原有验证，不能用 Swift `String` 的规范等价、类型相等、哈希或 ID 相同替代原始证据验证。每次追加仍检查请求、头部与资源预算、原有的每会话 ID 命名空间、`pageSelection`，以及全部新旧摘要和报告的来源、producer、引文、顺序及范围规则；原始帧、消息、未合并批次和选区不能由此变更。

追加仍按原有移除目标再追加的顺序生成完整 Document，以 sorted-key JSON 编码，保留 40MB 上限、原子写入和 `0600` 权限处理，持久化成功后才更新内存。它没有跨 Store 或跨进程的文件比较交换保证。模型批次、prompt、取消检查、逐批检查点和 legacy/latest 范围门槛没有因持久化优化而改变。

## 离线验证

运行 `bash Tests/ChatEvidence/run.sh` 与 `bash Tests/Contacts/run.sh`。生产 reader → store → summarizer → validated report 使用离线 fixture；模型只替换为严格 JSON 闭包。当前最终计数以本轮 output 的冻结日志为准，不能把历史检查数字当作新增真机结果。

`Tests/ChatEvidence/AppendTransactionChecks.swift` 为当前源码增加 103 项持久回归，并由上述 `ChatEvidence/run.sh` 直接编译执行；pass11 的完整 ChatEvidence 套件为 417 项。它用实际 Store 的通用完整保存路径对照受限追加，在固定 UUID/日期时逐检查点比较完整文件字节，并验证选中 ID 顺序、合法 ID 命名空间、坏产物拒绝、真实文件写入失败后内存不推进、两个总结任务在模型等待期间保存最新进度，以及取消后不保存。Unicode 反例保留了“类型相等但 UTF-8 不同”的请求：通用保存仍须由原生账号/帧验证拒绝，失败后同一 Store 的合法追加仍可成功。这些用例只使用合成证据、临时文件和本地模型闭包；它们不证明真机 OCR 覆盖、真实模型质量或手机耗时收益，较大合成历史也不扩大当前单页采集能力。

最新回归覆盖生产 profile→Messages→Reader→Store→注入式总结闭环：严格 latest 在 middle 或 oracle 恰为最新的页面都不从不可见事实升权，零读取/输入/模型调用；明确 currentPage 的2/3/5条上限只处理该页所选消息，固定绑定后读取/新增/改范围均拒绝，旧 complete/v2 latest 原文件逐字节保留、可导出但不再上传。选择的 scope/target/frame/pixelTime/limit/顺序/重复/缺失/越界 ID、raw升格和非选中消息的摘要/报告引用都必须拒绝。

独立 pass6 回归修复资料导航工厂曾将助手系统说明计入消息的问题，未将该问题算作 pass5 已修。实际生产导航→Reader→Store→严格引用总结使用合成页面和 echo 闭包验证：仅说明时0条/0模型，说明加一条真实样本时1条/1引用；无说明、同文系统区域外消息、普通联系人相同正文/几何、两个合格候选和错账号均有控制。新工厂规则只作用于新观察，不在 Store load/save 时重新分类：修复前真实生产路径保存的合成档中原有说明消息、pageSelection 和 v2 报告继续逐字节保留、可读及导出，不静默删除历史事实来源。

Reader4 既有回归覆盖：older/newer 的分离同文 AB 窗口（缺时间/相同时间），原始批次同事务隔离、禁止 raw 引用/升格、坏字段和合计预算拒绝、旧 v1 controlledScroll 档逐字节保存、真实ID可信边界控制、先匹配 overlap 后新ID冲突的 anchors 回滚、严格时间两侧/错误起点/未知/错序、分页结束不多滚动。联系人实际 RGBA glyph 检测仍经真实资料导航建立首帧身份证据；第二页 OCR 归档并暂停，不以图形识别成功冒充发生位置证明。

已有来源摘录、精确 tuple 去重、更正最后引文活动字段、旧 v1 与严格 v2 producer 标记、长会话分批、错误引用、未读媒介、缺/相对时间、模型失败与恢复、scope 不可扩张、联系人同名错号/缺专属结构/导航时序/换流换设备/取消/存档不可恢复 live 权限等检查继续保留。修改读取能力的测试同时保留真实ID可信边界的合法多页/增量控制，绝不向生产 OCR 注入 synthetic IDs。

尚未通过完整真机验收：实际微信版本/字体/主题下的完整气泡/媒介识别、滚动和会话边界、真实稳定平台消息ID与真实模型概括质量。授权过的单页真实测试与离线合成结果需分开报告；离线通过不代表已完整读取真实聊天，也不代表任务书实际耗时目标达成。
