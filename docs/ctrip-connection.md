# 携程连接

Phone Agent 的携程工具直接向携程问道官方接口发送旅行查询，支持机票、酒店、火车票和行程建议。手机运行时不依赖 Mac、Node.js、鼠标或浏览器登录态。它提供旅行参考信息，不把查询成功当成预订或付款成功。

## 在手机上使用

1. 打开「设置 → 携程连接」，保存申请到的携程授权码。已通过本机一次性导入的设备会显示「已保存携程授权码」。
2. 阅读说明并开启「启用携程查询」。更换授权码后需重新开启。
3. 在「设置 → 执行偏好 → 工具与状态显示」启用系统工具。只查询旅行信息时，可以开启「仅使用系统工具」，无需配件和屏幕共享。
4. 在同一对话中提出需求，例如「查询明天上海到北京的直飞航班，1位成人经济舱，优先比较价格和出发时间」。缺少必要条件时先追问；查询使用已有连接及宿主确认偏好。任务入口也可调用 `ctrip_query`。

「携程连接」页也提供固定上海景点问题的独立查询测试，结果只在本页显示。机票对话会使用打包的 [ctrip-travel Skill](../Skills/ctrip-travel/SKILL.md)，将完整条件发送给携程，并从真实回执生成航班卡片。

## 数据与授权

- 携程授权码保存在这台设备的独立钥匙串条目中，不复用模型 API Key，不进入任务参数、模型上下文、回执或项目文件。
- 查询文字发送给携程官方域名 `externalcallback.ctrip.com`。任务工具的查询结果会进入本机任务记录，并发给当前获授权的 AI 服务继续处理。
- 客户端只采用官方响应的 `result` 或 `result.content` 文本。其他调试字段、状态和原始错误不会进入任务记录。检测到授权码反射会拒绝采用整段结果。
- 固定 HTTPS 地址，拒绝重定向，响应上限 1 MiB，单次网络时限 45 秒；长文本明确标记截断。关闭连接或更换授权码后，进行中的旧结果不会再被采用。

## Mac 配置验证

独立配置工具位于 [Tools/Ctrip](../Tools/Ctrip/README.md)。它将授权码保存在 Mac 钥匙串，并支持本机页面和命令行查询。Mac 与 iPhone 的钥匙串独立。

开发版可通过 `provision_device.py` 将 Mac 钥匙串中的授权码经已配对的设备通道一次性导入同一用户的 iPhone App。Mac 的临时目录权限为 0700、文件为 0600，传输后立即清理；手机先移除一次性文件，再写入自己的钥匙串。仅 DEBUG 构建支持显式的一次性导入参数；导入不会开启携程连接、改变模型设置或代替用户同意。

`--test-ctrip-connection-once` 仅用于开发版手机的显式通用查询验证。安全回执只保留状态、时间、返回字符数和摘要，不包含授权码或响应正文。

## 航班卡片与连续追问

本轮目标是机票查询、卡片展示、连续追问和交接携程 App。卡片使用固定字段，涵盖标题、日期、起降时间、机场、舱位和参考价；推荐与补充说明放在卡片外。支持标题、紧凑列表、表格和同一时刻的代码共享票价子列表，不把网络参考航班当作携程可订结果。

同一对话保存每次实际发送的完整查询，包括零结果。最近一次查询的有序候选集用于“第二个”等追问；新查询替换旧候选，普通聊天不清空旅行上下文。打开旧对话时可重建旧格式卡片，保留原始消息与查询时间。

## 携程 App 交接

卡片先复制所选航班信息，再尝试原生入口。实际官方响应返回的极速版原生选价 URL，只有外层城市日期及 `c9` 内 `trip`、唯一 `flights[0]` 的 `flightNo`、起止城市、完整出发日期时刻、`class`、`seg`、`subChannelId` 均与下述来源事实范围一致时才优先保留；缺失或冲突时改用独立事实重建。不会把其他 metadata 中出现的航班号当成实际航班字段。只有来源明确的单一直飞航班、经济舱、绝对出发日期、唯一有效出发时刻和无冲突的大陆城市对，才生成下述事实查询描述。按钮为“打开这班航班”。该描述不携带价格、票种、订单、账号、签名或服务端令牌，也不选择某个票价政策。

当前候选入口为 `ctrippro://wireless/flight_inland_singletransition`，参数为 `c2=0`、`c3=<出发城市码>`、`c4=<到达城市码>`、`c5=<yyyyMMdd>`、`Channel=3`、`fromOpenUrl=1`、`routeCardVersion=G` 及 JSON 编码的 `c9`。已在官方安卓客户端实测的无价格描述为：

```json
{"trip":1,"flights":[{"seg":1,"fromCityCode":"SZX","toCityCode":"BJS","departureDate":"2026-10-27T21:00:00","subChannelId":3,"flightNo":"MF8350","class":"Y"}]}
```

`class=Y` 仅在来源明确经济舱时使用；其他舱位、时刻参考、缺少出发时刻、航班号或日期、来源与查询冲突，以及往返、中转、多程均不使用此重建路径。城市码来自携程官方大陆城市表，例如浦东/虹桥均映射 SHA，首都/大兴映射 BJS。人数、机场航站楼、实时票价及具体政策仍需在携程核对。

明确选择航班的卡片和口语入口只尝试该班原生选价页。真实 provider 入口被系统拒绝时，可尝试同一航班的独立事实重建入口；不会打开城市日期结果列表、通用机票首页或来源 HTTPS 资源，也不会把这些页面当作成功。城市日期列表参数仍用于本机验证和绑定路线日期，不能替代具体航班交接。系统接受 URL 时只报告“已发送打开请求”，不声称已经到达选价页。最终选票、填单和付款由用户在携程内完成。

缺少时刻、直飞、舱位或尚未核价时，只要原卡片仍可唯一确定航班号、城市对和绝对日期，即在手机上复用现有 `flightQuery` 做一次同班补查；客户端已有的网络重试上限保持不变，交接层不再循环查询。新返回必须明确给出完整的同班日期时刻、两端机场、直飞经济舱和真实报价，已知机场、起降时刻和日期不得被覆盖；相同 BJS 城市码也不能掩盖首都与大兴的变化。只在唯一匹配且原对话、原卡片、页面与前台授权仍有效时，才复制补查后的真实信息并尝试原生入口。补查不修改原卡片，不延长口语请求的原授权期限，也不需要 Mac 或自建服务。缺少绝对日期/城市对、补查失败、返回歧义或来源失效时明确结束本次尝试，不以仅复制代替可执行的补查。

## 报价缺失与时刻卡片复测（Build 96）

2026-10-25 对照携程发布的 1.0.1 官方脚本，固定 URL、POST、Content-Type 及 JSON 请求体在虚构凭据下逐项一致；官方 Node 脚本和当前原生 Swift 客户端均完成真实查询。未发现这几项请求结构错误，但不能据此排除服务端的其他内部原因。Mac 捕获到 HTTP 请求成功且通过业务封装检查、正文仍说明未取得机票数据而给出网络参考的返回；同条件多次调用也出现不同结果。

客户端还存在独立的展示问题，现已补齐“当前票价”、舱位内嵌票价、机场/航站楼、短机场名、全角分隔符及箭头时刻表等实际返回格式。报价卡片与时刻卡片分开：后者使用虚线边框、“时刻参考 · 尚未核价”和“票价待查”，按钮为“去携程查价”。无航班号但明确给出两个时刻和机场的参考表，也可生成时刻卡片，不编造航班号。原始消息保留；旧结果可按新解析器重新展示。

对话与任务中的携程查询路径遇到明确的服务端报价不可用、连接中途丢失、超时或成功响应中业务结果为空时，以相同查询共用最多一次自动重试；取消、授权变化会阻止重试。首次已有时刻参考而重试出现上述传输或空结果失败时，保留首次参考并明确未核价；两次均未取得结果时显示最终错误。无符合条件的航班、单独缺税费或行李、响应来源或格式异常、授权信息回显，以及 HTTP 授权、限流错误不触发该重试。自动重试的失败、恢复、上限和取消分支由离线测试覆盖；本轮升级后的真机查询没有触发此分支，不声称已在真实服务故障中验证恢复。

本轮手机执行 8 次真实查询，Mac 另执行 8 次，包括官方脚本和原生客户端对照。手机覆盖重复查询、中英文换路线和日期；后续两轮分别返回 5 和 10 张报价卡片。最终包回放修复了同一回复中 5 张报价与 1 张时刻参考的识别；真机确认两种样式及查价按钮打开携程。仍未验收航班预填、订单或付款页。返回的报价文本来自服务端，未独立验证库存。

新任务输入时欢迎区被隐藏、替代头像未挂载的问题也已修复。最终 Build 96 在 iPhone 17 Pro Max 验证键盘弹出后头像仍可见，并通过模拟器浅深色与最终包原生 UI 检查。完整请求对照、真实回执、旧结果回放、102 项展示检查、195 项协议/重试检查及数据核对见 [verification.json](../output/ctrip-reliability-avatar-20261025/verification.json)。
