# 独立规则核心与未来宿主适配

## 交付边界

`Sources/WeChatSkillCore` 是独立 Swift Package，只依赖系统 Foundation 与文件锁所需的 Darwin/Glibc，无第三方包。它不引用主工程类型、不运行模型、不采集画面、不识别 OCR、不执行鼠标/键盘、不发微信消息。`AtomicAction` 是内部 Swift 合同，不能直接当作 Sela 的动作 JSON；当前也没有对应注册工具。

Skill 正文已合并到主 App 的现有视觉任务加载入口，仍使用现有截图、输入、原生工具、队列和长任务机制。独立 Swift 规则核心和参考图分析器尚未链接进主 App，也没有对应注册工具或真实截图适配器；它们的离线检查不能冒充主 App 已经执行的软件闸口。

## 原子边界

`AtomicAction` 只允许单个 tap、longPress、定位 scroll、单字段 ASCII 输入、单个编辑键、一次剪贴板准备。不支持动作数组、回车提交、跨字段 Tab、多步骤宏或点赞并评论组合。

`AtomicActionRules.validateOrdinary` 拒绝所有具有提交语义的点击：sendMessage / sendComment / like / unlike。提交只由 `SubmissionCoordinator.take` 返回一个 tap。`unlike` 不在当前任务能力中。动作规则不执行输入，也不能保证调用者一定使用它；真实宿主应当只有一个受控派发出口，禁止旁路。

`FieldAccess` 区分未知、空、本次所有、其他草稿。普通输入/粘贴/删除需要真实焦点与可写归属。`focusedFieldID` 必须逐字对应当前实际输入框，不能只提供 focused=true。菜单粘贴还需 `ownerFieldID` 对应同帧的该输入框。中文通过独立 ClipboardLease + 可见粘贴菜单；lease 只说明已准备且尚无已知失效，不是当前剪贴板回读。后缀允许只有空格/换行，但不得为空字符串。最终原文核对仍必需。ASCII 单段上限 500 字节是对当前可选输入通道的限制，不是任务总长或总步数限制。

## 字段准备，不等于提交

`DraftPreparation` 从不可变 SkillTask 取得搜索关键词、消息原文或评论原文，不接收另一个随意替换的“目标文案”。它仅产生准备票据、准确剪贴板准备需求、待观察原因或原文已核验结论，不产生发送票据。

- `DraftScope` 绑定任务、设备/共享流和用途；消息/评论还需宿主已核对的账号与资料证明，评论还需本次动态绑定。搜索未核号时不伪造联系人身份。
- `DraftObservation` 是受信宿主的当前字段语义观察，沿用 FrameStamp / ObservedControl；真实字段种类必须与用途一致。`fieldBindingID` 对应同一实际字段，不能因局部控件 ID 相似就复用。
- 字段种类与输入法状态默认未知；未知字段、回复态、未完整读回或输入法组合态均不能报告完成。composing=false 必须来自实际观察。
- 焦点、长按菜单、全选、ASCII 输入或粘贴，每步只有一个动作。下一步要用新观察确认，不因动作返回就假定焦点/菜单/选区已经成立。
- 当前文本是本次原文的精确前缀且光标明确在末尾时，只准备后缀。剪贴板全文与所需后缀不同就要求重新准备；派发前已知剪贴板改变也会拒绝旧票据。空格与换行按原文保留，绝不以 Return 提交替代。
- 不同的外来草稿不覆盖，未知归属不自动领用。本次文本出错或光标不在末尾，有硬件键盘时可先独立全选并确认选区；纯鼠标缺少已观察的修正入口时保留内容并返回明确待处理原因，不编造菜单。
- 输入派发后不见变化就保持待核验，不再给同文输入。完整正确的实际回读可结束准备，部分正确回读才允许继续剩余段。准备结论不是消息/评论已发送，也不是新的提交授权。
- 准备票据只在当前进程内消费一次，取消/暂停应调用 invalidate。可选择持久化草稿检查点；新进程必须显式重新核对后恢复，不能恢复旧准备票据。

上述对象仍需真实宿主适配，不证明像素真实性。此版只提供规则与合成回放，未接入真实手机输入。独立宿主也不得把 preparation 的 verified 直接转成业务完成。

## 草稿检查点与跨进程恢复

`DraftCheckpointStorage` 有 MemoryDraftCheckpoint 与 FileDraftCheckpoint 两个实现。显式传给 DraftPreparation 后，保存不可变原任务、绑定历史、最后实际回读与待核验输入意图。每次派发原子输入前先保存意图；保存失败或写入结果未知都不向宿主返回动作，并作废当前会话。

文件实现与提交账本共用内部 LockedJSONFile，采用文件锁、revision 比较、原子替换与 0600 权限；草稿与提交分别保存。已有草稿文件不能通过新建会话静默清空，损坏文件也不覆盖。保存的是审计证据，不是防篡改凭证；外部编辑的 JSON 不能成为实际观察。

`DraftPreparation.restore` 的要求：

- 原任务字节完全一致、用途和设备一致，账号逐字相同。新资料证明的 ID、像素与确认时间必须是新的，晚于最后检查点；只重确认旧资料像素不能恢复。
- 追加新的绑定历史，保留旧回读与未知意图。旧坐标、fieldBindingID、票据、焦点、选区或剪贴板 lease 都不会用于派发；恢复的第一步仍是当前新图读取。
- 文本输入前后的回读相同时继续待核验，不自动重输。实际完整回读正确可结束准备，实际部分回读则按当前末尾光标与归属只补后缀。
- 朋友圈评论另需新的动态绑定、已完整阅读的原动态正文，以及宿主确实覆盖所请求范围的候选证据。全正文、日期、显式年份、已有配图描述等需相符，候选仍有歧义则拒绝恢复编辑。覆盖未知/局部、旧正文不完整、图片型动态没有可核对正文，均保留待重新确认；本版没有图片内容等价识别或平台永久动态 ID。
- 请求包含发送时，恢复必须查询实际 JournalStorage。缺少提交状态返回 submissionStateUnknown；相关效果已提交/失败/待核验返回 submissionNeedsReview；已核验完成返回 effectAlreadyCompleted，不再填写。只要求草稿时不额外索取发送授权。

每次输入派发前再次读提交状态。两份文件不是跨文件事务，宿主仍须维持同一任务的独占和输入串行；此组件不替代宿主队列，也不声称提供跨进程微信执行互斥。恢复时发现提交待定先暂停准备；可交给下面独立的只读核验器，而不是重填文案。

独立包带有 `wechat-draft-recovery-probe`，固定使用 fixture/offline：一个进程保存意图并退出，另一个进程加载磁盘检查点。它检查草稿未变化/部分完成/完整回读，以及提交结果未看到/仍等待/已正常显示六种情况。不执行返回的输入动作，也没有 live 模式；只能证明语义检查点与只读恢复分支，不能证明手机输入、真实重启或微信结果。

## 提交结果的跨进程只读核验

`RecoveredResultReader` 只有观察和作废接口，没有 reserve、take 或任何手机动作出口。它只处理已经向宿主交出单次点击、仍为 pending / uncertain 的既有操作。仅预留尚未交出点击的记录、或已经终态的记录，不通过此接口重启流程；用户可以读取账本查看原状态。

- 新会话先用新资料证明核对原账号；资料像素与确认必须晚于原结果或上轮核验。朋友圈另需新的动态绑定、完整原正文和已实际覆盖所请求范围的候选证据，沿用草稿恢复的排歧条件。
- 原提交前画面、账号证明、点击时间和原会话结果全部保留；新证据独立追加到 `recoveryReviews`，不能把新图改写成旧 proofID、旧共享流或旧时间。`result` 字段继续保留原会话的证据，可能为空；终态可由经过校验的最后恢复观察支持。
- `VisibleItem` 的 ID 仅限本帧。本模块对字节相同的文本、作者和可见顺序计算唯一的历史对应，不直接比较新旧本地 ID。
- 单聊还需提交前已记录的 `VisibleLandmark`：实际时间文字或明确会话起始结构，包含真实来源、帧 ID 及前后相邻项。在两个画面中匹配时间文字和相邻关系，可以区分同文消息；有多个有效历史对应、旧项没保留或标记不符时继续未知。
- 旧账本只有 `continuityAnchors` 本地字符串、没有原始结构化标记时，返回 baseline_landmarks_missing；不从当前图倒填旧证据。`listVerifiedEmpty` 必须代表宿主确实证实相关历史集合为空，不是当前截图某块区域看起来空。`correspondenceUnambiguous` 也不能在尚未排除其他历史片段时设为 true。
- 评论以经过重新确认的原动态为上下文，仍核对旧可见评论的顺序及新增本人项。图片型动态缺少可核对正文、相关范围不完整或相同候选无法区分时，不能自动通过恢复核验。
- 只有唯一新增本人原文且状态正常才为 verified；明确新项失败则 failed；仍等待、只有他人同文或没有新项均为 uncertain。点赞只读核对同一动态当前本人点赞状态，不点击菜单中的取消/点赞。
- 同一只读会话可用后续更晚的新像素继续核验；换设备/共享流或重新开会话需重新核对身份。取消或保存失败会作废读取器；未知保存结果由重新读取账本判断，不触发重新输入。
- 账本同时验证状态与恢复证据，恢复观察只能追加、不能删改，终态不可回退。草稿恢复器读到已核验完成就返回 effectAlreadyCompleted，不再填原文。

这些规则是对受信宿主语义证据的一致性校验，不是微信平台消息 ID、像素真实性、已送达/已读或点击因果的证明。宿主须确认历史窗口确实对应原范围；日期缺年、重复时间组或隐藏项无法排除时，应保持未知。真实画面识别与端到端验收仍未完成。

## 数据所有权

| 数据 | 谁产生 | 本模块处理 |
|---|---|---|
| SkillTask | 宿主从真实用户指令与澄清建立 | 检查原请求、不可变任务 ID、允许的效果及准确文字 |
| FrameStamp | 真实采集宿主 | 区分 liveDevice / fixture / referenceImage；校验设备、共享流、像素/确认时间 |
| ObservedControl | 当前帧 OCR 或真实本地图形检测 | 校验本帧、坐标范围、唯一 ID、来源、语义角色 |
| ContactBinding | 识别完整当前资料并核号的适配器 | 核对账号/姓名、绑定本任务；登记进程内身份 |
| MomentCandidate | 实际列表/详情与导航连续证据 | 按账号、原始日期、显式年份、文字与图片线索保守匹配 |
| SceneObservation | 真实页面适配器 | 核对绑定、页面、草稿、本人结果及前后连续性 |
| OperationRecord | 本模块 | 提交前持久化、单次派发、独立结果、恢复不重发 |

这些都是**受信宿主输入合同**。给 JSON 手写 `liveDevice`、`ocr`、`myself`、`correspondenceUnambiguous: true` 不会把模型推测变成实际证据。核心不能从结构体真实性推导像素真实性。后续适配器必须只从自己的采集与检测闭包构建它们，不接受模型生成的证明对象。当前没有这个适配器，所以尚无真机可用路径。

## 目标与匹配

- 联系人候选仅来自 Contacts；唯一候选只允许进一步打开资料，不代表核号完成。未知账号候选与准确账号候选同时存在时仍待区分。
- `ContactQuery.expectedName` 是需要逐字核对的实际资料名称，不应把未解析的备注直接填入。备注与昵称的对应由宿主保留真实证据；未知时先搜索，不强制要求账号输入。
- 本次 ContactBinding 与 SkillTask 的完整规范化 JSON 字节绑定，不能把 Alice 的资料用于另一条 Bob 任务。账号和原文按 UTF-8 精确比较，不折叠大小写、不作 Unicode 规范化。
- 任一可能候选尚缺资料/正文/年份时，不能让另一条看似唯一的候选胜出。`noneInObservedRange` 仅表示这次候选范围，不能宣布全量不存在。
- MomentBinding 是运行内 UUID，不是微信动态 ID。日期原样保存，没有年份保持 nil。媒体描述是宿主对已实际查看内容的受信摘要，字符串相同不提供图片识别或永久去重保证；图片歧义应继续人工/视觉辨认。
- 当前核心接收已解析的具体线索；它不解析自然语言相对日期，不替“最新”验证排序，不做截图识别。这些属于未来宿主的任务解释与观察职责。不得用“第一条”伪造已解析的具体目标。

## 提交生命周期

1. 新图核号后 `bindContact`；需要朋友圈则在真实详情与候选排歧后 `bindMoment`。旧档案不自动注册。
2. `reserve` 校验当前本次目标、提交授权、准确草稿、顶层评论对象、当前可见发送控件；先写 pending，再给进程内 ticket。已点赞直接写 alreadySatisfied，不产生 ticket。
3. `take` 再核对同一帧/字段与时效，先销毁本次 ticket，持久化派发意图，然后只返回一个 tap。票据不可复用；保存失败、取消、变帧、换绑定都不返回 tap。
4. 宿主执行单个输入。HID 成功只表示输入链路，不能改成 verified。
5. `verify` 用提交后真实新像素与当前绑定核对结果。消息/评论必须有可连续对应的前后列表、唯一新增本人同文项和正常状态；旧项、他人项、两个相同新项、滚动断链或等待状态均 uncertain。明确新项失败则 failed。点赞以该动态的本人点赞状态为准。
6. uncertain 可在同一有效身份与目标绑定下继续只读核验。相同任务+效果槽不会产生第二次提交；换 operation UUID 无法绕过。点赞+评论任务先核验点赞，再独立提交评论。

此协议提供“不自动重复派发”的控制，不提供微信端 exactly-once。崩溃可能发生在保存之后、实际点击之前，也可能发生在点击后但结果还未读取，二者都必须保留待核验。

## 持久化与重启

FileJournal 使用显式指定目录、文件锁、revision 比较与原子替换；数据文件权限 0600。并行旧版本写入会被拒绝，损坏 JSON 保留且不覆盖。调用者应为每个独立账本提供自己的目录。

每次写入最多推进一个操作阶段；不能删除或重排历史，不能改写原任务、联系人、动态、草稿或原始画面。派发时间一旦写入就保持不变，verified / failed / alreadySatisfied 为终态，不可回退。运行时与归档读取共用结果证据规则，归档自称成功但观察并不支持时拒绝读取。结构一致性仍不等于外部数据真实性。

档案不含可复用派发票据。暂停、停止、取消和换设备/共享流时，宿主必须调用 `invalidateLiveContext`，清除运行内身份、动态绑定和未消费票据，保留账本。单纯取消一个调用不是宿主生命周期集成的替代品。

核心在入口遇到取消也会立即清除运行内绑定和票据。待核验可继续只读确认，但每次结果的像素时间与系统确认都必须严格晚于上次结果，帧 ID 也必须不同；重放旧结果不会写入新记录。

对于提交账本，新进程需要新的真实身份与动态绑定。旧 pending 不能自动发送，也不能直接把旧绑定 UUID 重新登记为 live；没有人工强行改写成功/重新授权重试的公共 API。具备新的独立证据时可由 RecoveredResultReader 只读核验，缺失证据则保留原状态/待核验；不能为了跑通而清账本。为证明资料到目标页的连续性，目标页像素必须晚于本次资料确认；仅系统重确认旧聊天图不能继承身份。

Journal 是调用者拥有的本地工作状态，不是抗篡改安全日志。结构校验能拒绝损坏/矛盾记录，不能证明被外部编辑的内容是真的。宿主不得把任意导入 JSON 或模型生成的档案当成完成证据。

## 未来接入端口

适配器只需把已有宿主能力映射到下列职责，无需在本模块重建它们：

- 观察端：当前整屏、设备/共享流、真实时钟、OCR/图形来源、遮挡、当前控件与身份/目标连续性。
- 输入端：把一个通过校验的 AtomicAction 映射为一个已有动作；串行、绑定相同设备、保留宿主取消与释放机制。剪贴板准备和粘贴分别映射。
- 状态端：真实用户任务、当前确认模式、草稿归属、已确认子任务、单个 JournalStorage。

接入需要以后单独实施：App skill 选择/打包、真实资料/朋友圈解析、原子动作桥接、UI 动作识别后的提交闸口、原始画面到 DTO 的不可伪造边界，以及 iPhone 验收。这里仅定义边界，不创建空的可执行适配器或默认“成功”实现。
