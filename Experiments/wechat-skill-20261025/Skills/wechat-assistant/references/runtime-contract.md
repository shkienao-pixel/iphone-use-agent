# 独立规则核心与未来宿主适配

## 交付边界

`Sources/WeChatSkillCore` 是独立 Swift Package，只依赖系统 Foundation 与文件锁所需的 Darwin/Glibc，无第三方包。它不引用主工程类型、不运行模型、不采集画面、不识别 OCR、不执行鼠标/键盘、不发微信消息。`AtomicAction` 是内部 Swift 合同，不能直接当作 Sela 的动作 JSON；当前也没有对应注册工具。

Skill 正文可以由一个具备真实工具的视觉宿主使用；规则核心是以后接入时可选的守门组件。当前两者都未加入主 App。仅阅读参考架构，不复制现有截图、输入、原生工具、队列或长任务实现。

## 原子边界

`AtomicAction` 只允许单个 tap、longPress、定位 scroll、单字段 ASCII 输入、单个编辑键、一次剪贴板准备。不支持动作数组、回车提交、跨字段 Tab、多步骤宏或点赞并评论组合。

`AtomicActionRules.validateOrdinary` 拒绝所有具有提交语义的点击：sendMessage / sendComment / like / unlike。提交只由 `SubmissionCoordinator.take` 返回一个 tap。`unlike` 不在当前任务能力中。动作规则不执行输入，也不能保证调用者一定使用它；真实宿主应当只有一个受控派发出口，禁止旁路。

`FieldAccess` 区分未知、空、本次所有、其他草稿。普通输入/粘贴/删除需要真实焦点与可写归属。中文通过独立 ClipboardLease + 可见粘贴菜单；lease 只说明已准备且尚无已知失效，不是当前剪贴板回读。最终原文核对仍必需。ASCII 单段上限 500 字节是对当前可选输入通道的限制，不是任务总长或总步数限制。

## 数据所有权

| 数据 | 谁产生 | 本模块处理 |
|---|---|---|
| SkillTask | 宿主从真实用户指令与澄清建立 | 检查原请求、不可变任务 ID、允许的效果及准确文字 |
| FrameStamp | 真实采集宿主 | 区分 liveDevice / fixture / referenceImage；校验设备、共享流、像素/确认时间 |
| ObservedControl | 当前帧 OCR 或真实本地图形检测 | 校验本帧、坐标范围、唯一 ID、来源、语义角色 |
| ContactBinding | 识别完整当前资料并核号的适配器 | 核对账号/姓名、绑定本任务；登记进程内身份 |
| MomentCandidate | 实际列表/详情与导航连续证据 | 按账号、原始日期、显式年份、文字与图片线索保守匹配 |
| SceneObservation | 真实页面适配器 | 核对绑定、页面、草稿、本人结果及前后连续性 |
| OperationRecord | 本模块 | 提交前持久化、单次派发、独立结果、恢复不重发 |

这些都是**受信宿主输入合同**。给 JSON 手写 `liveDevice`、`ocr`、`myself`、`correspondenceUnambiguous: true` 不会把模型推测变成实际证据。核心不能从结构体真实性推导像素真实性。后续适配器必须只从自己的采集与检测闭包构建它们，不接受模型生成的证明对象。当前没有这个适配器，所以尚无真机可用路径。

## 目标与匹配

- 联系人候选仅来自 Contacts；唯一候选只允许进一步打开资料，不代表核号完成。未知账号候选与准确账号候选同时存在时仍待区分。
- `ContactQuery.expectedName` 是需要逐字核对的实际资料名称，不应把未解析的备注直接填入。备注与昵称的对应由宿主保留真实证据；未知时先搜索，不强制要求账号输入。
- 本次 ContactBinding 与 SkillTask 的完整规范化 JSON 字节绑定，不能把 Alice 的资料用于另一条 Bob 任务。账号和原文按 UTF-8 精确比较，不折叠大小写、不作 Unicode 规范化。
- 任一可能候选尚缺资料/正文/年份时，不能让另一条看似唯一的候选胜出。`noneInObservedRange` 仅表示这次候选范围，不能宣布全量不存在。
- MomentBinding 是运行内 UUID，不是微信动态 ID。日期原样保存，没有年份保持 nil。媒体描述是宿主对已实际查看内容的受信摘要，字符串相同不提供图片识别或永久去重保证；图片歧义应继续人工/视觉辨认。
- 当前核心接收已解析的具体线索；它不解析自然语言相对日期，不替“最新”验证排序，不做截图识别。这些属于未来宿主的任务解释与观察职责。不得用“第一条”伪造已解析的具体目标。

## 提交生命周期

1. 新图核号后 `bindContact`；需要朋友圈则在真实详情与候选排歧后 `bindMoment`。旧档案不自动注册。
2. `reserve` 校验当前本次目标、提交授权、准确草稿、顶层评论对象、当前可见发送控件；先写 pending，再给进程内 ticket。已点赞直接写 alreadySatisfied，不产生 ticket。
3. `take` 再核对同一帧/字段与时效，先销毁本次 ticket，持久化派发意图，然后只返回一个 tap。票据不可复用；保存失败、取消、变帧、换绑定都不返回 tap。
4. 宿主执行单个输入。HID 成功只表示输入链路，不能改成 verified。
5. `verify` 用提交后真实新像素与当前绑定核对结果。消息/评论必须有可连续对应的前后列表、唯一新增本人同文项和正常状态；旧项、他人项、两个相同新项、滚动断链或等待状态均 uncertain。明确新项失败则 failed。点赞以该动态的本人点赞状态为准。
6. uncertain 可在同一有效身份与目标绑定下继续只读核验。相同任务+效果槽不会产生第二次提交；换 operation UUID 无法绕过。点赞+评论任务先核验点赞，再独立提交评论。

此协议提供“不自动重复派发”的控制，不提供微信端 exactly-once。崩溃可能发生在保存之后、实际点击之前，也可能发生在点击后但结果还未读取，二者都必须保留待核验。

## 持久化与重启

FileJournal 使用显式指定目录、文件锁、revision 比较与原子替换；数据文件权限 0600。并行旧版本写入会被拒绝，损坏 JSON 保留且不覆盖。调用者应为每个独立账本提供自己的目录。

档案不含可复用派发票据。暂停、停止、取消和换设备/共享流时，宿主必须调用 `invalidateLiveContext`，清除运行内身份、动态绑定和未消费票据，保留账本。单纯取消一个调用不是宿主生命周期集成的替代品。

新进程需要新的真实身份与动态绑定。旧 pending 不能自动发送，也不能直接把旧绑定 UUID 重新登记为 live；本版没有人工强行改写成功/重新授权重试的公共 API。需要继续处理旧待核验效果时，由未来适配器建立新的独立核验依据，或向用户报告状态；不能为了跑通而清账本。为证明资料到目标页的连续性，目标页像素必须晚于本次资料确认；仅系统重确认旧聊天图不能继承身份。

Journal 是调用者拥有的本地工作状态，不是抗篡改安全日志。结构校验能拒绝损坏/矛盾记录，不能证明被外部编辑的内容是真的。宿主不得把任意导入 JSON 或模型生成的档案当成完成证据。

## 未来接入端口

适配器只需把已有宿主能力映射到下列职责，无需在本模块重建它们：

- 观察端：当前整屏、设备/共享流、真实时钟、OCR/图形来源、遮挡、当前控件与身份/目标连续性。
- 输入端：把一个通过校验的 AtomicAction 映射为一个已有动作；串行、绑定相同设备、保留宿主取消与释放机制。剪贴板准备和粘贴分别映射。
- 状态端：真实用户任务、当前确认模式、草稿归属、已确认子任务、单个 JournalStorage。

接入需要以后单独实施：App skill 选择/打包、真实资料/朋友圈解析、原子动作桥接、UI 动作识别后的提交闸口、原始画面到 DTO 的不可伪造边界，以及 iPhone 验收。这里仅定义边界，不创建空的可执行适配器或默认“成功”实现。
